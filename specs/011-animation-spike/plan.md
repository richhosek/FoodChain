# Implementation Plan: Side-by-Side Animation Spike

**Branch**: `animation-spike` (actual Git branch); `011-animation-spike` (feature identifier) | **Date**: 2026-11-16 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/011-animation-spike/spec.md`.

## Summary

Build an isolated, reproducible comparison of the existing Phaser Canvas board, an optimized shared-frame paramecium, and a forced Phaser WebGL candidate. Compare one artist-authored rigged or deforming character when the owner approves an available tool. Measure identical dense paramecium, dense amoeba and mixed workloads, preserve required behavior, and document physical-device results and owner judgments. Prototype equivalent Godot workloads only when the specified failure or owner-complexity trigger occurs; missing evidence remains pending. Do not migrate production.

## Technical Context

**Language/Version**: TypeScript 6.0.2; Node.js >=24.16 and <25 for the existing browser project. A conditional Godot prototype may use its supported scripting language only within the isolated evaluation.

**Primary Dependencies**: Existing Phaser 4.1.0, Vite 8.3.8, Playwright 1.65.1. No new dependency, tool installation, paid license, upload or engine upgrade is authorized by planning. Rive is a provisional authored-study proposal, not an accepted dependency.

**Storage**: Local experimental fixtures and result files, generated assets kept under an isolated experiment directory; no gameplay persistence or production asset overwrites.

**Testing**: Node `node:test` for deterministic fixtures, metrics and decision logic; Playwright desktop and mobile emulation for workload and interaction parity; physical iPhone and Android plus desktop browser testing; existing typecheck, unit suite, build and focused regression checks.

**Target Platform**: Browser-first desktop and mobile, mouse and touch; record physical device/browser/OS and test configuration. Godot only as a conditional, isolated comparison.

**Project Type**: Isolated experiment alongside the existing client-side game; production engine and rendering remain unchanged.

**Performance Goals**: Per candidate/workload/device, at least 95% of all unfiltered foreground intervals <=33.4 ms over >=30 seconds, with nonzero samples and no visibility loss. Record p95/p99, max, input latency, loading, assets and memory where available; do not claim a hardware pass from emulation.

**Constraints**: 64 cells, fixed 800x800 logical board and 100-unit cells; same seeds, board positions, starting visual states, control script and display conditions for matched trials. Preserve approved art, rank sizing, independent gaze/blink/body motion, effects, reset/cancel, gameplay outcomes and full-cell interaction. No production changes or unattended overwrite of existing assets.

**Scale/Scope**: Three 64-creature workloads for each candidate and available configuration, plus one representative authored character. The Godot prototype is conditional; it is not a migration.

## Constitution Check

**Before research: PASS, subject to execution and review.**

- **Rules**: Reuse deterministic domain fixtures and compare outcomes; do not modify game mechanics.
- **Mobile-first and cross-input**: Browser TypeScript remains the first production target; include mouse, real touch and desktop/mobile verification, explicitly distinguishing emulation.
- **Engine evaluation**: Retain the production engine while comparing specified alternatives; record animation states, transitions, square/hex implications, supported platforms and ownership costs before any future engine decision.
- **Mechanics before art**: Preserve independent game rules and existing approved art; the rigged study is separately scoped.
- **Reproducibility**: Freeze workload, seeds, initial visual states, timing scripts and measurement definitions; report raw data and unsupported metrics.

## Design and Validation Sequence

1. Establish a fresh baseline with the actual production Canvas `BoardView` in a blank same-origin page. Verify one scene, correct renderer, source identity and no duplicate game; use frozen deterministic workloads and a controlled ready barrier.
2. Define fixture IDs and deterministic visual state, required 64/64/mixed compositions, consistent rank bounds, seeded interaction and effect timeline. Add tests for fixture reproducibility, candidate teardown, timestamp calculations, invalid trials and decision-state transitions before comparing performance.
3. Implement an isolated shared-frame paramecium adapter and a forced `Phaser.WEBGL` adapter, preserving independent blink/gaze/body motion, selection, flash, drag/cancel, refill/reset and deterministic game outcomes. Test actual renderer and explicitly report unsupported features and context loss; do not assume production Canvas-composite texture uploads are efficient on WebGL.
4. With owner/artist approval and suitable license, select and document one authoring tool; create one comparable rig/deform study from copied approved art, record creation and revision effort, export terms, versions and limitations, and integrate it into the workload matrix. If unavailable, record blocked and leave that comparison pending.
5. Execute each candidate/workload serially with matching seed, viewport, DPR, warm-up, cache and input schedule; retain raw foreground intervals and visibility. Report device, browser, renderer, initial readiness and comparable asset/load/memory methods, plus visual checklist and input latency. Validate on real iPhone, Android and desktop; report missing devices explicitly.
6. Apply the decision contract: verified WebGL failure or owner rejection of complexity triggers an equivalent isolated Godot scene before any migration decision. Missing evidence alone produces pending. Capture results, costs and owner sign-off; run focused and production regressions without altering production assets. No result or hardware availability is presumed by this plan.

## Constitution Check After Design

**PASS by design, subject to measured validation.** The TypeScript browser game and independent rules remain the production baseline, mobile and cross-input validation are planned, and engine/animation selection remains open pending evidence. Any Godot work is an isolated comparison; a future production language or platform change would require separate approval and constitution review. No exception is proposed.
